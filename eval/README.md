# `eval/` — re-derived results from the Canonical Repair Library

These scripts re-derive, from the **committed** artifacts in `grouping/out/`, quantities the paper
previously asserted without measuring. They make **no external calls** and read **no claim-level
data**, so they run unchanged against the public anonymized release.

## Running

```bash
python -m venv .venv && .venv/bin/pip install "pandas>=2.0,<3" numpy matplotlib

PYTHONPATH=eval .venv/bin/python eval/a1_critic_posthoc.py        # add --data-root <dir> to retarget
PYTHONPATH=eval .venv/bin/python eval/a2_separation_guard.py
PYTHONPATH=eval .venv/bin/python eval/a3_confidence.py
PYTHONPATH=eval .venv/bin/python eval/a4_library_audit.py
PYTHONPATH=eval .venv/bin/python eval/a5_savings.py
PYTHONPATH=eval .venv/bin/python eval/a6_region_decomposition.py
PYTHONPATH=eval .venv/bin/python eval/figures.py
```

`--data-root` defaults to `grouping/out`. Each script writes CSV/JSON to `eval/out/` and replaces its
own section in `eval/RESULTS.md` (re-runs are idempotent). `--no-append` prints without writing.

Figures land in `figures/`. The two pre-existing figures are regenerated by the repo's own script,
which now honours `CRP_FIG_DATA` / `CRP_FIG_OUT`:

```bash
CRP_FIG_DATA=<data-root> CRP_FIG_OUT=figures .venv/bin/python figures/make_figures.py
```

Pinned to `pandas<3`: pandas 3 infers `StringDtype` where the existing suite expects `object`, which
fails `tests/test_bigquery_tool.py`. Analysis outputs are byte-identical under 2.3.3 and 3.0.5.

## The v2 rebuild (library of record)

`rerun_full_chain.py` re-runs the **real Orchestrator** (7-agent chain, 2-repair prompt, in-loop
critic with the bounded revision round) over every GOLD signature and writes a complete artifact set
to `grouping/out_v2/` — `golden_solutions.csv` (v1 schema + `critic_verdict`, `revised`),
`llm_cache.jsonl` (resumable; the run's reproducibility record), `rerun_manifest.json` (model,
temperature, prompt hash, counts), plus copies of the library-independent artifacts so `out_v2/` is
a complete `--data-root`. A `--heal-rounds` pass retries signatures whose LLM call degraded to a
shell, mirroring the June batch's only-ok-counts-as-done semantics; surviving shells ship and are
counted honestly. `a7_rerun_churn.py` then quantifies v1→v2 churn (split agreement, how the 388
truncated splits resolved, cost stability) and gates the paper swap. `make_public_basis.py` writes
`grouping/out_v2_public/` with dollar columns rescaled to the public-release basis.

Regenerate savings for v2 (env overrides are honoured by `src/config.py`):

```bash
CRP_GOLDEN_SOLUTIONS=grouping/out_v2/golden_solutions.csv \
CRP_GROUP_SAVINGS=grouping/out_v2/group_savings.csv \
.venv/bin/python grouping/12_group_savings.py
```

## What each script establishes

| Script | Question | Headline |
|---|---|---|
| `a1_critic_posthoc` | Would the critic have passed what was emitted? | 4,804 PASS / 261 FLAG / 5 FAIL; demotes 4 repairs that carry `usable=True` with no cost median (99.98% → 99.90% coverage) |
| `a2_separation_guard` | Does the τ=1.5 guard establish that two repairs exist? | No — 67.6% of *never-proposed* signatures already clear τ; AUC 0.535, and 0.509 on clean two-repair proposals |
| `a3_confidence` | Does the artifact implement the printed confidence equation, and does support saturate? | Matches `stats_tool.py` on 5,066/5,066 comparable rows; saturates for only 23.8% |
| `a4_library_audit` | What degenerate rows and structural artifacts exist? | 1 empty-text (an abstention), 1 unusable, 388 truncated 3-repair splits, and a cost-basis mismatch between the two artifacts |
| `a5_savings` | Is the measured overspend concentrated severity or just volume? | Volume — size predicts total overspend (0.72) but not per-claim severity (0.12) |
| `a6_region_decomposition` | Is a repair-independent regional multiplier defensible? | Weakened — labor and material offset (r = −0.28) and cost *composition* varies 2.5× across states |

## Two constraints that must be respected

**Cost basis.** `canonical_repairs.csv` and `golden_solutions.csv` do **not** report costs on the same
basis — they agree on 1 of 2,082 single-repair signatures, with the CRL running ~2.4× higher at the
median. The agent chain uses `gsar_tot_cost_gross` (`config.COST_COL`), which
`11_reassemble_from_cache.py` documents as the corrected basis; the CRL predates that correction.
**Any cost statistic for the emitted library must come from `golden_solutions.csv`.** Mixing the two
silently inflates costs and corrupts any dispersion analysis built on CRL quartiles.

**Post-hoc, not in-loop.** `a1` applies the critic to the *finished* library. It cannot reproduce the
bounded revision round, because a revision would change the LLM text and the batch's
`llm_cache.jsonl` no longer exists. Claims about in-loop behaviour need a live re-run.

**NaN is not None.** A missing cost median must round-trip as the same falsy-or-not value assembly
produced: `not float('nan')` is False but `not None` is True, so coercing NaN to None while rebuilding
solution dicts silently changes which critic gate fires. `_solution_dict` reconstructs the distinction
from the released `usable` flag — the only surviving record of which one assembly emitted. Getting
this wrong flips a reported finding without changing any headline count, so it is easy to miss.

## Provenance note

The released `golden_solutions.csv` was produced by `grouping/10_golden_solutions.py` (a standalone
batch script whose inlined prompt permits up to three repairs) replayed through
`grouping/11_reassemble_from_cache.py`, which imports `StatsTool` and `SolutionAssemblyAgent` but not
`SolutionCriticAgent`. The separation guard, cost bands and confidence in the released artifact are
therefore genuine agent code; the critic gate is not, which is why `a1` exists.
